# Workspaces, capacity, and scheduling

## Preserve one source of ticket state

Send workers the absolute canonical ticket path and their separate code checkout path. Resolve ticket links relative to the canonical ticket file, not the worker's current directory. Worktree copies of tickets and `INDEX.md` are not independent trackers. If a worker cannot access the canonical files, establish a single-writer handoff transport before dispatch; do not let copied trackers diverge.

## Workspace policy

Reuse the project's established workspace policy and user-selected checkout. Inspect status and existing changes before dispatch.

**Default: serial use of the supplied checkout.** Allow one implementation writer, then freeze that checkout for review. After review, its code is already present for a later ticket using that checkout. No commit is needed to record an uncommitted snapshot. Preserve unrelated user edits and establish a reproducible baseline for each ticket, so the next diff does not attribute earlier work to the new ticket.

The only same-checkout exception is a registered intra-ticket delegation group. It does not make the checkout generally shared or available to another ticket. Apply the group rules below before dispatching a child; otherwise retain one implementation writer and the normal review freeze.

**Parallel use:** the coordinator creates or assigns one exclusive Git worktree per concurrent implementation agent before dispatch. Reuse an existing worktree only after verifying its ownership, contents, and base. Being in a linked worktree does not make it free for a second writer. For a non-Git project, require an established equivalent isolation method; otherwise run serially. Never fall back to concurrent writes in the supplied checkout when worktree creation fails.

Before allocation, inspect `git worktree list --porcelain`, each candidate's repository root, status, branch or detached state, and resolved base revision. Resolve physical paths so aliases do not count as different checkouts. Check the run journal and actual runtime ownership, including workers outside this run. Use an established workspace claim mechanism when present. A RUN.md entry or Git worktree lock alone does not prevent another agent from writing. Unknown ownership blocks reuse.

Prefer native workspace tools that preserve the current task and assignment model. Otherwise use Git's worktree commands. Use the registered external workspace's `worktrees/<assignment-id>/` location, or the host's established external worktree location recorded in RUN.md. Do not put generated workflow records or new worktrees inside the product source tree. Do not create user-owned conversations, commit ignore-file changes, force an occupied branch, or reset an existing branch to allocate a workspace. Select a unique assignment branch or a recorded detached base. Inspect applicable setup hooks before creating or preparing the workspace; allocation does not authorize application startup or unrelated installation.

Record allocation intent with the assignment, intended path, and base before creation. Confirm the actual worktree identity and contents before dispatch. If creation fails or its outcome is unknown, inspect the intended path and worktree inventory before retrying; preserve partial state and do not allocate a duplicate blindly.

Start from an exact verified base containing the prerequisites. A worktree from HEAD does not include uncommitted prerequisite changes. The standing local execution authority permits local commits and integration of reviewed ticket work, but never silently discard, stash, reset, overwrite, or copy over unrelated user work to construct a base. If the required base cannot be prepared safely, use serial work when it meets the request or report the specific conflict.

Before parallel dispatch, record how each result will reach the selected local consumer. The run's standing local execution authority permits the coordinator to make local commits and serialize merge or cherry-pick integration of identified reviewed ticket commits into that consumer. Do not ask for approval for those actions. Do not move an explicitly chosen consumer to another branch merely to avoid a conflict, overwrite unrelated user work, rewrite history, push, open a pull request, deploy, or mutate shared infrastructure without separate authority.

Record the integration target and permitted local operations. Integrate only identified reviewed changes within the standing authority. Reserve the destination and serialize integration into it. Do not integrate, rebase, or change the base of a checkout used by an active or uncertain implementer, reviewer, or verifier. Conflicts or combined behavioral changes go back to an assigned implementer; the coordinator does not invent a fix during a merge. Recheck affected tests and review evidence on changed results before treating them as ready. Write the allocated integration `handoff.json` with the exact destination identity, reports, checks, skips, and cleanup; then set the ticket's relative `integration_ref` to it. Availability alone and a clean merge do not prove integration or verified behavior.

## Test resources and ownership transfer

A lack of dependency edges does not make parallel execution safe. Before dispatch, inspect command/configuration sources for mutable resources beyond the checkout: build outputs, temporary directories, ports, databases, queues, Docker volumes and bind mounts, external test accounts, and expensive test-suite capacity. Treat broad race suites, full repository checks, and other CPU-, memory-, I/O-, or timing-intensive commands as named test lanes with an owner and concurrency policy even when they use no fixed port or database. Resolve effective paths and identities, not just labels. Two Compose project names do not isolate an explicitly shared volume or host directory. Shared repository configuration and refs also need coordination; worktrees do not isolate them.

Record each reservation in RUN.md: resource or test-lane identity and host, owning assignment, permitted use, isolation or concurrency settings, current state, and release condition. Supply supported per-assignment test settings and output paths to workers. Keep credentials out of the record. Use the project registry/index's state-independent reservation table to discover claims from active, closing, and completed workflows with retained resources. Under the short project metadata lock, recheck conflicts and record each new claim before allocation or dispatch; release the lock before slow operations. Keep uncertain claims and incomplete metadata updates visible. Workflow completion does not release a resource. Check conflicts with all active or uncertain implementation, review, and verification runs, not just this ticket set. Resources proven read-only or safe for concurrent use can be shared. Isolate mutable resources; if isolation is unavailable, reduce concurrency before dispatch. Do not weaken tests or change product behavior to create apparent isolation.

When broad race or full suites overlap and expose a failure, retain the exact commands, timing, environment and dependency identities, logs, and competing suites before changing execution. Investigate under the original concurrent conditions. A later serial pass does not erase the concurrent failure; it supplies another observation. Classify the event as a product race, test synchronization defect, resource collision, or unrelated pre-existing failure only from evidence. Reserve serial execution after that investigation when shared capacity is the cause, while keeping meaningful concurrency regression coverage.

An implementer owns code writes only in its assigned checkout and its permitted canonical ticket fields. It uses the reserved resources and reports unexpected conflicts to the coordinator. The coordinator confirms the writer and its mutating child processes stopped before freezing the target for review. One reviewer covers both axes by default. When risk requires two reviewers, both may read that same stable checkout; separate worktrees are not required for read-only inspection. A bounded reviewer repair is the sole review-stage write exception: the coordinator grants its exact temporary lease only after every required reviewer finishes independent first inspection, and no other writer may overlap it. Give concurrent checks isolated mutable resources, or run those checks in sequence. The single combined reviewer, or the behavior reviewer in a two-reviewer assignment, owns application startup by default. Resource reservations never override a stage's execution limits.

Keep the checkout reserved until all reviewer processes have stopped and cleanup is confirmed. For a revision, reuse the same worktree and preserved edits when valid. A replacement checkout or base requires a new recorded assignment attempt and verified handoff; workers must not relocate themselves. Unknown liveness retains reservations. A final message or elapsed time alone does not release them.

Retain worktrees by default through review, revisions, and integration handoff. Only the coordinator or established workspace owner may retire them under the agreed cleanup policy. Confirm all users stopped, code and evidence are retained, and canonical references remain valid. Never force-remove dirty worktrees, delete the sole implementation copy, or run broad pruning as routine cleanup. Record retained resources and unresolved cleanup on pause or completion.

Git mechanics reference: [git-worktree](https://git-scm.com/docs/git-worktree). Project authority and the stage limits above still govern their use.

## Intra-ticket delegation groups

One implementation assignment remains the ticket owner. Prefer separately reviewable vertical tickets for separable outcomes; use a delegation group when one cohesive slice still benefits from independent bounded work. Grant only the `child_capacity` that the proposed work can use efficiently after reserving actual runtime slots, counting the coordinator plus every currently active or uncertain implementer, child, reviewer, and verifier, and proving that the group's mutable resources can be isolated. Do not hold future review slots idle while an isolated implementation group can use them; drain the whole group before review and then reuse the released slots for the required reviewers. `child_capacity` is a coordinator-owned ceiling, not an entitlement: the owner cannot create capacity, borrow a slot from another assignment, or continue using a revoked allowance. It stays zero when independence, isolation, or capacity is unavailable. Count running and uncertain children against total runtime capacity and the registered child allowance. They count against an explicit implementation-agent limit when the user defined that limit to cover all implementation runtimes; otherwise the default one-at-a-time rule limits ticket owners, not registered children.

Allow children only for work that is independent at an observable behavior or established interface-contract boundary. Different paths, modules, or test names alone do not establish independence. Do not delegate work that needs concurrent changes to a shared schema, public contract, generated repository-wide output, ticket state, dependency graph, or the same behavior under test.

Before dispatch, the coordinator records a delegation-group entry in `RUN.md`, reserves its capacity, and gives the owner the permitted dispatch-handoff transport. The owner supplies the work details through that transport. Record the parent assignment and runtime identity, ticket, checkout identity and base, every child ID and goal, expected child handoff, exact leased paths, preserved interface contract, isolated mutable test/output resources, runtime-slot reservation, and parent/child agent paths. Leases must be exact and pairwise non-overlapping after resolving physical paths; a directory lease includes all descendants. Resource reservations remain in the `RUN.md` reservation map and child handoff. When the dashboard is enabled, require each child to use its progress record with recorded ancestry, ticket, role, stage, state, summary, timestamps, next action, and applicable file lease.

After the coordinator grants and registers the group, the ticket owner may dispatch children directly within the recorded `child_capacity`; it does not need a separate coordinator dispatch for each child. Before the runtime call, the owner records dispatch intent through the permitted handoff transport. Immediately after it returns, the owner records the actual result there, including a runtime ID when returned or an unknown outcome when it is not. The coordinator records that intent/result and observes liveness in `RUN.md`. The owner must not exceed the grant or dispatch a child with unregistered leases, contract, or resources.

Children in a group may use the owner's checkout only under that registration. Each child writes only its leased paths and assigned scratch/output locations. It must not commit, switch branch, rebase, merge, reset, stash, alter refs or worktrees, or otherwise change Git state. It must not write ticket files, `RUN.md`, lifecycle fields, dependencies, shared schemas, or repository-wide generated output. The parent must not write a child's leased paths while that child is running or uncertain. Each child uses only its own reserved mutable test resources and output paths. The parent uses a distinct reservation or waits for sequenced access; it never uses a child's reservation concurrently. Run checks sequentially whenever their effective resources overlap. The parent remains the sole ticket-lifecycle and final-implementation-record writer.

Children cannot spawn children. A child runs its local TDD cycles inside its leased behavior boundary and returns red/green evidence, changed paths, checks, cleanup state, blockers, and its handoff through its registered records. The parent does not integrate opportunistically: after all children are confirmed stopped, it inspects every handoff, resolves the work within its own authority, and runs cross-boundary plus required implementation checks. The coordinator freezes the checkout for review only after every group member and every mutating child process has stopped and cleanup is confirmed. Unknown liveness retains the slot, lease, checkout exclusion, and resource reservation; it is not a clean handoff or reviewable target.

On a discovered lease, contract, output, or resource overlap, stop affected writes, ask those children to checkpoint, and preserve their edits and evidence. Do not resolve the overlap by silently editing another lease or relaxing a test. The coordinator records the incident, reconciles liveness and physical resources, then either reschedules with new disjoint registration or reduces work to the parent/serial execution. If the coordinator revokes a child's allowance, use [live instruction delivery](run-state.md#live-instruction-delivery) to request that child checkpoint and stop; retain its slot, lease, checkout exclusion, and resource reservation until stop and cleanup are confirmed. For a failed or unknown child dispatch, apply the run-state dispatch and recovery rules before retrying; never assume that a missing response released its lease.

When a ticket-owning parent reports high context pressure, it checkpoints its location, checks, blockers, next action, and group state at the next meaningful boundary. The coordinator may preserve, reduce, or revoke `child_capacity` based on work and isolation risk, not a fixed token threshold. Let the runtime manage compaction. The same parent continues after runtime compaction when safe; if it cannot continue, confirm it stopped before assigning a replacement and re-register every continuing child's ancestry, lease, resource reservation, and liveness. Never leave two live ticket owners or dispatch a new child merely as a context workaround. Exact telemetry is advisory and unavailable telemetry is reported as unavailable, not estimated.

## Availability

`ready` establishes review completion. `available` records access in the agreed consumer base. They are independent.

Before starting a dependent, verify its actual checkout contains the exact required implementation and compatible prerequisites. For committed work, inspect revision relationships and any intervening changes. For dirty work, compare the recorded paths and content identity and inspect changes that can affect the required contract. File presence alone is insufficient.

A single availability flag cannot describe every checkout. Use it for the documented agreed base, record per-consumer evidence in `RUN.md`, and check each actual assignment. If that base or producer implementation changes, invalidate stale availability evidence before scheduling. Clear any live `integration_ref` in the same update that clears `available`; preserve its manifest path as history under the entrypoint's reopening rule. Code on an inaccessible branch remains unavailable, even after review passes.

Shared serial work can change an earlier ticket's code. Check impacts on earlier acceptance criteria and downstream dependencies. Reopen affected review evidence when required; do not preserve a ready claim for an invalidated implementation. Full feature verification remains separate from per-ticket checks.

## Dependency-based scheduling

Block work only on a concrete source, artifact, resource, or acceptance dependency. Record the missing producer or reserved identity and the observable condition that clears it. An active reviewer does not automatically block isolated work, including independent tooling development.

Separate development from adoption. Independent tooling development may proceed under its own assignment when its ownership, checkout and file leases, resources, and runtime capacity are disjoint. Adopting that tooling into an active assignment changes its inputs or scope; do so only at an acknowledged safe boundary through [live instruction delivery](run-state.md#live-instruction-delivery), after reconciling the worker's current command and resources. Until then, the active assignment keeps its acknowledged inputs.

Eligibility still preserves the single-writer workspace policy, resource isolation, and expensive test-lane concurrency limits above. If any of those concrete constraints overlap, sequence the affected work; do not infer a broader dependency between otherwise independent assignments.

## Capacity and selection

Use actual runtime capacity. Count active and uncertain implementation assignments against the user's implementation limit. Count reviewers and the coordinator against the runtime's total limit. User permission for two implementers does not imply room for two implementers plus two reviewers.

An active or uncertain final verifier also consumes runtime capacity and reserves its combined code target and mutable test resources. Do not dispatch a writer or conflicting test run into that reservation. Use the same dispatch recovery rules without changing a ticket's assignee for verification.

The coordinator also acts as the review parent. Reserve one reviewer slot by default, and require that reviewer to cover both axes. The coordinator decides and records whether security, concurrency, migration, financial, public contract, large cross-subsystem, uncertainty, or explicit-policy risk requires two independent reviewers; the implementer does not choose. If capacity is tight, let current implementers finish and release their slots before a required review; do not keep future reviewer slots idle during safely isolated implementation. When two reviewers are required but the runtime permits them only in sequence, follow review-ticket's independence and stable-target rules. Tool failure is not a reason to relax a risk-triggered two-reviewer requirement.

Select pending tickets from validated candidates. Prefer a small ready slice that releases blocked consumers, then a revision that can close cheaply, while aging independent work to avoid starvation. Compare expected implementation, check, review, and integration effort with the dispatch overhead; parallelize only when ownership, capacity, and resources make a useful overlap possible. For revision_required or confirmed stopped in_progress work, explicitly recheck prerequisites, external blockers, checkout ownership, and pairwise resources; the validator's pending-only candidate list does not schedule them automatically.

Record selection before dispatch. Re-read the target ticket and relevant prerequisite state to detect concurrent edits. Do not claim multiple tickets from an old index snapshot. A confirmed resource conflict is a blocker even if the validator's labels missed it.

Use the longest safe event wait when there is no useful local coordination work. A slow worker may be making progress. On an unchanged wait, do not re-read unchanged artifacts or rebuild a status summary. Do not emit another status message; wait again. Inspect evidence before interrupting; do not launch a second worker because the first exceeded an invented time estimate. When a tool failure repeats without changed conditions, save the blocker instead of busy polling.

At completion or a recurring bottleneck, summarize measured effort from existing run, progress, and handoff evidence: dispatches and review returns, waiting versus implementation/check time when recorded, repeated expensive checks and their reason, actual overlap, and integration conflicts. Identify the next useful sizing or scheduling adjustment. Keep unmeasured costs unknown; no new tracker or invented speedup is needed.

## Handoff shape

Include PROJECT.md, WORKFLOW.md, the absolute canonical workflow directory, external context path, and separate code root with every assignment. Ticket, progress and report paths remain external; never substitute a workflow slug relative to the code checkout. When telemetry is enabled, supply the resolved heartbeat command and verify its returned output path stays in that workflow.

Every assignment uses one canonical contract. Supply the stage skill path; canonical ticket or verification target; code checkout, verified base, and branch or detached state; assignment ID; canonical agent path and canonical parent agent path; reserved test resources and output paths; applicable project constraints; exact handoff path; exact pause-checkpoint path when allocated for a pause; coordinator-resolved dashboard availability; exact progress path when enabled; and coordinator-owned `child_capacity`. State the permitted lifecycle and file writes, required result and cleanup evidence, and the next stage the worker must not start. For implementation, include the TDD companion and require the worker to verify the assignment before edits. For review, state that reviewer children return structured axis reports and evidence to the review parent; they do not write the parent-owned review manifest.

Runtime launch settings come from the runtime's current command help or an existing verified project launcher. Keep automatic context management in the runtime's supported named/default mode. Ticket sizing estimates, context-window guesses, and telemetry never become numeric compaction arguments or token-triggered checkpoint instructions. Worker prompts name semantic checkpoint conditions such as a completed acceptance-criterion slice, a completed check, or a handoff boundary. Follow run-state's [transition checkpoints](run-state.md#transition-checkpoints). Context size alone does not end an assignment. The same worker continues after runtime-managed compaction; replacement requires an actual inability to continue and confirmed old-owner stop.

For a revision, add the exact report and handoff-manifest paths, changed paths, required prior finding IDs and dispositions, affected contracts, reusable evidence candidates, and required rechecks. For re-review, give reviewers that same delta. Apply the shared [check scope and evidence reuse](../../setup-workflow/references/check-scope.md) contract. The reviewer independently validates reusable evidence. Do not paste the entire prior conversation. For review, use review-ticket's role briefs and report contracts, with a stable code target and canonical ticket path.

Maintain minimal coordinator context: policy, mappings, dependency facts, findings that need a decision, and artifact pointers. Checkpoint at meaningful boundaries and let the runtime manage compaction. The same coordinator resumes from the compact checkpoint and actual runtime state. Only when the runtime truly cannot continue may a confirmed-stopped coordinator be replaced under the run-state recovery rules; a large context alone never triggers transfer.
