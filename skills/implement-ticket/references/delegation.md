# Controlled intra-ticket delegation

Use this reference only when the coordinator has recorded a positive `child_capacity` for your implementation assignment and you have independently observable behavior or contract work. The default remains one implementer in one context. Delegation is a narrow same-checkout exception, not permission to parallelize a ticket because it has several files.

## Keep one ticket owner

You remain the ticket owner. Only you update the ticket's lifecycle fields and final implementation record. The coordinator owns runtime capacity, `RUN.md`, checkout and resource reservations, and the delegation-group registration. A child cannot spawn another child, change the ticket, change `RUN.md`, or revise the dependency graph.

Before asking the coordinator to register a child, identify a package whose result can be observed separately through an established behavior or interface contract. State the acceptance behavior, contract to preserve, exact leased paths, isolated mutable test/output resources, goal, and expected handoff. Different filenames do not prove independence. Do not delegate packages that need concurrent changes to the same behavior, public or shared contract, schema, generated repository-wide output, or mutable test resource.

Wait for the coordinator's registered group, runtime-slot reservation, and permitted dispatch-handoff transport before dispatch. The registration must name the parent and child identities and ancestry, ticket, checkout/base, `child_capacity`, child goal and handoff, pairwise-disjoint exact file leases, preserved interface contract, and isolated resources. Once those records exist, you may dispatch children directly within the allowance. Record dispatch intent in the supplied transport before each runtime call and its actual result immediately afterward; include the runtime ID when returned, or preserve an unknown outcome. Capacity is a runtime ceiling owned by the coordinator. Do not infer extra capacity or exceed the grant.

## Operate a same-checkout group safely

Each child writes only its leased paths and assigned scratch/output locations. A directory lease includes every descendant. A child must not commit, switch branches, alter refs or worktrees, rebase, merge, reset, stash, or otherwise change Git state. It must not edit canonical ticket files, `RUN.md`, dependencies, shared schemas, or repository-wide generated output.

While a child is running or its liveness is unknown, do not write its leased paths. Each child uses only its own reserved mutable test resources and output locations. Use a distinct parent reservation or wait for sequenced access before running a parent check; never use a child's reservation concurrently. Run checks in sequence whenever their real resource identities overlap, even when their labels differ. Do not weaken a test or change production behavior merely to make resources appear isolated.

Each child uses the TDD companion locally: choose an observable behavior inside its lease, observe the focused test fail before production behavior changes, make it pass, and run affected regressions. Its dashboard progress record contains only supported progress fields, including milestone summary, blocker when applicable, and file lease. It records detailed red/green evidence, changed leased paths, checks, resource/process cleanup, and its handoff in the registered child handoff; resource reservations remain in `RUN.md`. It does not write the ticket implementation record.

Update child progress only at meaningful milestones: assignment accepted, behavior located, failing test observed, implementation underway, checks running, blocked, checkpointed, or handoff complete. The record must retain its agent path, parent agent path, ticket ID, role, stage, state, summary, started and updated times, next action, and applicable file lease. The coordinator observes runtime liveness as well as progress; a stale record alone does not prove a child stopped.

If a child discovers any lease, contract, generated-output, or resource overlap, stop affected writes and checkpoint. Report the conflict with the paths/resources and current evidence. Do not edit across the lease boundary. Preserve edits and test evidence while the coordinator reconciles runtime liveness and resources. Resume only with an updated, disjoint registration or serial parent work. If the coordinator revokes the allowance, request the affected child to checkpoint and stop. Retain its slot, lease, parent write exclusion, checkout reservation, and test resources until its stop and cleanup are confirmed. Unknown dispatch or liveness receives the same retention until recovery proves otherwise.

## Integrate, freeze, and continue

Do not integrate child work while group members are running or unknown. After every child is confirmed stopped and each mutating child process is cleaned up, inspect each child handoff and its leased changes. Resolve integration within the ticket scope, then run cross-boundary tests and all required implementation checks. Record the combined test-first and final-check evidence once in the ticket's final implementation record. Review can begin only after the coordinator confirms the whole group is shut down and the checkout is frozen.

Use exact latest-call input telemetry when available as an advisory signal; cumulative usage is not context occupancy. Under high context pressure, checkpoint your location, checks, blockers, next action, group membership, leases, resources, and each child's liveness at the next meaningful boundary. Let the runtime manage compaction. If integration or another bounded step is almost complete, finish the bounded step and record it first when that is safer than interrupting the transition. Continue as the same owner after compaction when safe. Use a fresh context only when the runtime cannot continue cleanly: request children to checkpoint, let the coordinator drain or reconcile the group, confirm the old owner stopped, and have the coordinator re-register continuing ancestry, leases, resources, and liveness before a replacement writes. Two ticket owners must never be live together. Do not spawn children as a context workaround. When telemetry is unavailable, report it as unavailable and do not estimate token pressure.
